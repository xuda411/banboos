# Banboos 2.0 账号登录与用户管理路线

当前版本的 API token 只用于预发布联调，不能作为上线后的用户身份。正式服务器版本采用“账号 + 身份提供方 + 租户角色 + 可撤销会话”的模型。

## 登录方式

- 手机号验证码：接入短信服务商，手机号只保存规范化值的哈希和验证时间。
- 邮箱验证码：接入邮件服务商，邮箱只保存规范化值的哈希和验证时间。
- 微信一键登录：接入微信开放平台 OAuth 回调，保存 openid / unionid 的哈希，不在前端保存密钥。
- API token：仅保留为开发联调 fallback，生产环境关闭。

前端已提供三种登录方式切换、验证码输入、服务状态提示和开发令牌折叠入口。短信、邮件和微信供应商未配置时，接口明确返回“待配置”，不会伪造发送成功。

## 已落地的服务器基础

- `user_accounts`：账号状态、显示名、创建时间、最近登录时间。
- `user_identities`：手机号、邮箱、微信等身份提供方与账号的唯一绑定。
- `user_memberships`：账号、租户、角色和成员状态。
- `auth_challenges`：验证码哈希、过期时间、尝试次数、消费时间和请求来源。
- `auth_sessions`：短期访问会话对应的可撤销刷新令牌哈希。
- `user_audit_logs`：登录、退出、绑定、角色变更和管理员操作审计。

本阶段新增身份输入基础服务：手机号/邮箱/微信标识在进入适配器前统一规范化，数据库只使用带密钥 HMAC 的 `subject_hash`，界面只接收脱敏值；验证码请求提供可注入时钟的冷却和窗口频控策略。短信、邮件、微信供应商仍未配置时，接口继续返回明确的待配置状态，不会生成假验证码。

迁移文件为 `0002_identity_service`。当前管理接口 `GET /api/v1/admin/users` 返回预览数据，正式启用时改为 PostgreSQL 查询并增加分页、筛选、禁用账号、角色分配和审计查询。

## 上线前必须完成

1. 接入短信、邮件和微信 OAuth 适配器，密钥放在服务器密钥管理中，并配置 `BANBOOS2_IDENTITY_HASH_SECRET`（至少 32 位）。
2. 使用短期 access token + 可撤销 refresh token；验证码限频、单次消费、失败锁定和 IP / 设备风控必须在服务端执行。
3. 将管理员操作绑定 `user_id`、`tenant_id`、`request_id`，并保留导出、调度和权限变更审计。
4. 关闭生产 API token fallback，完成跨租户、过期会话、验证码重放和越权测试后再开放生产控制。
